# 副作用を確かめる

テストが通っていても、テストに入れた例しか確かめていない。この skill は、テストの外にある文章で変更前後を比べ、変更が意図しない文章にどう効くかを確かめる。

一度、`metaphor-verb` のルールが参考元のコーパスで「誤検知0件」になったことがあった。そのコーパスの例をそのままテストに入れていたので、0件になるのは当然だった。テストの外で「前の方に倒れた」「二人の関係が壊れた」を試すと、どちらも拾っていた。確かめる文は、実装やテストを見る前に、変更の目的から考えて書く。

## 1. 何を変えたかをつかむ

```bash
git diff <base>...<head> -- scripts/polish.py
```

変更を次のどれかに分け、下の観点を選ぶ。複数に当てはまれば、すべて見る。

- 診断ルールの追加・変更（`inspect` の正規表現、除外条件、`RULE_CATEGORY`）
- 照合の変更（`verify` の数え方・正規化・保護対象）
- 評価シートの変更（`report`）

## 2. 試す文を書く

変更の目的とは逆の側の文を、少なくとも観点ごとに2つずつ書き、scratchpad のファイルに保存する。拾ってほしい文も数個入れ、絞りすぎていないか確かめる。

### 診断ルールのとき

- **文字どおりの使い方**: 物の動作（倒れる、壊れる）、薬・酒・冷房が効く、料理で溶かす、身体の話。
- **人が普通に使う言い方**: 人間関係や感情（関係が壊れる、信頼が壊れる）、AIが広まる前から定着している慣用句や業界の言い方（安全側に倒す、骨が折れる）。この診断は「AIに多い型」を探すので、人が普通に書く言い方を拾うのは誤りになる。
- **形の揺れ**: 方向・位置の語が付く形（右側に倒す、前の方に）、活用（倒し・倒さ・倒れ）、敬体と常体、漢字とひらがな。
- **保護領域**: 「」の引用、インラインコード、コードブロック、表、リンクの中で指摘が出ないか。
- **Markdown の構造**: 複数行にまたがる太字や箇条書き、見出し。
- **他のルールとの重なり**: 同じ箇所に別のルールの指摘が二重に出ないか。

### 照合のとき

- **慣用句**: 数を数えていない語（一人ひとり、一日中、十分）を言い換えたときに止まらないか。
- **保護対象**: 引用・コードの中は一字一句守る対象。正規化などの処理が、ここでの書き換えを見逃さないか。
- **正しい言い換えと本当の変更**: 同じ意味の言い換え（一回→1回）で止まりすぎないか。値が変わる書き換え（三回→5回）を通さないか。
- **表示**: `review` や `diff` に、正規化した後ではなく原文が出ているか。

### 評価シートのとき

- 分類ごとの件数が変わるので、過去のシートと数字を比べられなくなる範囲を書き出す。

## 3. 変更前後で同じ文章を処理する

`scripts/compare.py` は、git の参照（変更前）と作業ツリー（または `--head` の参照）の `polish.py` を両方読み込み、同じ文章を処理して差を出す。ブランチを切り替えずに使える。

辞書のパスは `~/.local/bin/polish-japanese`（導入時に作られるラッパー）の中に書かれている。`PY=` の Python と、最後の行の `--dic`・`--user-dic` をそのまま使う。

```bash
C=.claude/skills/check-side-effects/scripts/compare.py
# 診断の差：ルールごとの件数と、増えた（+）・消えた（-）指摘を文つきで出す
$PY $C analyze main probe.md README.md references/*.md --head feature/x --dic ... --user-dic ...
# 照合の差：書き換え前後の組（同名ファイル）ごとに、verify の判定の変化を出す
$PY $C verify main --pairs before_dir after_dir --head fix/x --dic ... --user-dic ...
```

辞書ありと `--lightweight` の両方で流す。名詞の連なりなど辞書に頼るルールと、固有名詞の保護は、辞書の有無で結果が変わる。

文章は次を使う。

- 手順2で書いた試す文
- このリポジトリの Markdown（README.md、references/*.md、SKILL.md）
- 参考元のコーパス: `git clone --depth 1 https://github.com/nanaism/yomiyasu` を scratchpad に置き、`tests/corpus/` の `human`（人の文章）、`raw_ai`（AIの出力）、`edge_cases`（文字どおりの使い方）を使う。照合の比較には `raw_ai` と `yomiyasu_rewritten`（書き換え後）を組にする。使うのは文章だけで、コーパスのスクリプトは実行しない

増えた指摘（+）と消えた指摘（-）は、件数だけで判断せず、1行ずつ文を読んで、意図した変化か誤検知・見逃しかを決める。

## 4. 並行するブランチを確かめる

同時に進めているブランチがあれば、一時ブランチでまとめてマージし、テストを流してから消す。

```bash
git switch -c tmp/merge-check main
git merge --no-edit <branch-a> <branch-b> ...
python3 -m unittest discover -s scripts -p 'test_*.py'
git merge --abort   # 衝突したとき
git switch main && git branch -D tmp/merge-check
```

追跡していないファイルがある状態で `git stash` してブランチを切り替えない。追跡していないファイルは stash の別の親に入るので、`git checkout stash@{0} -- <path>` では戻らない。その後に stash を消すと、ファイルを失う。ほかのブランチの変更を比べるなら、`compare.py --head` か `git worktree` を使う。

## 5. 見つけたら

誤検知や見逃しは、直す前に失敗するテストとして加える（Red を確かめてから直す）。条件を絞って直したときは、絞ったことで拾わなくなった文（見逃し）も探して報告する。

## 報告の形

```markdown
## <ブランチ名>（<変更の要約>）

| 文 | 結果 | 判断 |
| --- | --- | --- |
| （試した文） | （検出された箇所／止まった・通った） | 誤検知・見逃し・意図どおり |

- 変更前後の差: （compare.py の件数の表の要点）
- 確かめた範囲: （使った文章と、辞書あり・なし）
- 確かめていない範囲: （残っている心配）
- 直すなら: （具体的な案）
```

副作用が見つからなかった観点も「確かめた範囲」に書く。見つからなかったことと、確かめていないことを区別するため。
